# Bold Template Pack

This pack brings the `beautiful-html-templates` design systems into the
`powerpoint-slides` skill without making them the default for every deck.
The design documents were written for HTML decks; the skill treats them as
design recipes and rebuilds each system natively in PowerPoint.

## What To Read

1. Read `bold-template-pack/selection-index.json` first.
2. Shortlist candidates from metadata only:
   - `mood`
   - `tone`
   - `best_for`
   - `avoid_for`
   - `formality`
   - `density`
   - `scheme`
3. For title-slide previews, read only the relevant candidate `preview.md`
   files.
4. After the user chooses a bold template, read exactly that one template's
   full `design.md`. Its first section, **PowerPoint Translation Policy**,
   explains how every CSS device in the document maps to a PowerPoint
   construct.
5. Do not read every `design.md` in the pack.
6. Do not read or copy `template.html` from the source template library; the
   skill never produces HTML.

## How To Use In PowerPoint Slides

Preview mix:

- 1 safe option from `STYLE_PRESETS.md`
- at least 1 bold option from this pack
- 1 wildcard option, which may be another bold template from this pack or a
  self-generated custom design

Adjust the tone inside that default mix:

- For board, legal, regulatory, healthcare, investor-update, or highly formal
  internal decks, make the safe option very restrained and choose calmer,
  higher-formality bold templates. The wildcard should feel authoritative and
  specific, not merely decorative.
- For bold, editorial, expressive, experimental, or highly designed decks, keep
  the safe option as a readable fallback, choose one strong bold template, and
  use the wildcard for either a second adventurous template or a custom design
  that better matches the user's occasion and vibe.

If the wildcard is custom, it must follow the skill's no-slop aesthetics:
distinctive typography, a committed palette, a recognizable layout system, a
context-specific visual idea, and no visible process labels such as "custom",
"wildcard", "template", or "preview".

## Implementation Contract

`design.md` is the design-system reference. Treat it as a style recipe, not as
content to copy. `preview.md` is only a lightweight style card for generating
the three title-slide options.

Preview slides must be real title slides for the user's deck, built as
one-slide `.pptx` files and rendered to PNG with `scripts/render-pptx.py`. Do
not render template names, option labels, file names, paths, `preview.md`,
"generated from", or user requirement notes on the slide itself.

When generating final slides:

- Output is a native `.pptx` on the 13.333 × 7.5 in (16:9) `LAYOUT_WIDE`
  canvas, generated by a `build-deck.js` (pptxgenjs) script and finished with
  `apply-theme.py` and `add-animations.py`. See `pptx-template.md`.
- Translate the template's CSS measurements with: px ÷ 144 = in, px ÷ 2 = pt,
  1 vw = 0.133 in = 9.6 pt, 1 vh = 0.075 in = 5.4 pt. Viewport-fluid rules and
  breakpoints are ignored; the canvas is fixed.
- Write the template's palette into the theme (`lt1` default surface, `dk1`
  ink, `lt2`/`dk2` alternate surface and ink, `accent1` the accent) so the
  user can recolor from PowerPoint's Design tab.
- Use the template's font families by name. Check installation with
  `scripts/list-fonts.py`; if a family is missing, say so and use an
  Office-safe face so the render is honest.
- Gradients, blurred blobs, grid and noise textures become background images
  from `scripts/make-background.py`, applied on layouts.
- Preserve the selected template's fonts, palette, decorative vocabulary,
  spacing rhythm, and component grammar as real shapes, lines, and text —
  never as screenshots.
- Keep the user's actual slide content primary. The template style should
  shape presentation, not override message or structure.
- Verify rendered output (`scripts/render-pptx.py`) for text overflow, panel
  overlap, and font fallback. `check-pptx.py` passing is necessary, not
  sufficient.
